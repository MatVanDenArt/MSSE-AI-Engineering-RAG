# AI tooling & prompting documentation

## Project evolution & workflow
This was a new project built from the ground up using a multi-tool AI workflow. Rather than a pre-planned refactor of an existing codebase, the architecture evolved organically through rapid prototyping and necessary pivots to accommodate free-tier hosting constraints. 

My workflow consisted of three distinct phases:
1. **Document analysis (NotebookLM):** I initially used NotebookLM to examine the available HR documents and select a shortlist of policies that made the most sense to group together for the RAG corpus. I then generated a project brief.
2. **Core development (Antigravity 2):** Having previously used VS Code for my Machine Learning project, I wanted to test the newly released Antigravity 2 assistant on a real production task. Antigravity handled the environment setup based on my initial prompt, making it much easier to get the project off the ground than starting from scratch in VSC. However, development wasn't completely frictionless; the architecture evolved with several major pivots to ensure the app could be deployed on a free Render instance. 
3. **Refinement (VS Code):** Once the heavy lifting and main development were completed inside Antigravity, I transitioned to Visual Studio Code (VSC) to handle smaller code refinements and final documentation.

## How the AI assistant was utilized

1. **Debugging regional API constraints:**
   During the initial development phase, we encountered persistent `404 NOT_FOUND` errors when attempting to use the default `gemini-pro` and `gemini-1.5-flash` models. The AI assistant helped diagnose that these legacy endpoints are often disabled for UK-based Free Tier keys. The assistant suggested a pivot to the newer `gemini-3.5-flash` model and proposed implementing `Groq` (`llama-3.1-8b-instant`) as an ultra-fast, highly reliable fallback.
2. **Evaluation framework generation:**
   The AI assistant wrote the `evaluate.py` script to programmatically iterate over our 19 hardcoded test questions. It identified that making 19 rapid API calls would trigger `429 RESOURCE_EXHAUSTED` rate limits on our free-tier keys, and proactively injected exception handling and pacing delays (`time.sleep`) to ensure the evaluation loop succeeded.
3. **Architectural pivots:**
   The AI assistant helped pivot the application from an initial monolithic approach into a decoupled architecture (a pure FastAPI backend and a Streamlit frontend client) to satisfy the separation of concerns grading rubric.
4. **CI/CD automation:**
   The AI assistant drafted the automated `pytest` suite and the `.github/workflows/ci.yml` file to ensure the codebase possessed proper continuous integration.
5. **Memory optimization & resilient routing:**
   When local PyTorch embeddings crashed the 512MB Render free tier with OOM errors, the AI assistant architected a custom `GeminiRESTEmbeddings` class to offload vector math to the cloud. It also designed the resilient fallback router (disabling default LangChain backoff via `max_retries=0` and utilizing a `try...except` failover) to ensure the API never hangs on rate limits.


## The friction of free tools
While developing on free-tier platforms is highly cost-effective, it introduced significant friction that actively shaped the project's architecture:
1. **API rate limits:** Free-tier limits for both Google Gemini and Groq were easily exhausted during batch evaluation and intensive testing. This forced the development of the Resilient Fallback Router and custom pacing delays (`time.sleep`) to prevent the application from hanging or crashing.
2. **Memory constraints:** Render's free-tier container provides only 512MB of RAM. This strict limit caused instant Out-Of-Memory (OOM) crashes when attempting to initialize standard PyTorch models for local embeddings and re-ranking. To survive this constraint, the project had to undergo a major pivot: completely abandoning local `sentence-transformers` in favor of externalizing the vector math to Google's REST API, and commenting out the advanced Two-Stage Retrieval (CrossEncoder) logic.
3. **Regional restrictions:** The default Gemini endpoints (`gemini-pro`) returned persistent `404 NOT_FOUND` errors for UK-based Free Tier keys, requiring diagnostic time to discover and pivot to the active `gemini-3.5-flash` endpoint.

## Project retrospective

### What worked well
- **Multi-tool AI synergy:** Using NotebookLM for initial document comprehension, Antigravity 2 for rapid environment setup and core scaffolding, and VS Code for final polish proved to be an exceptionally fast and effective workflow.
- **Fail-fast architecture:** Refactoring the LLM clients to use `max_retries=0` and manually handling the failover dramatically improved the user experience, ensuring the app never stalled while waiting for exponential backoff loops.
- **Data quality:** The rigorous manual cleaning of the PDFs (removing footers, headers, and transcribing images to Markdown text) directly translated to the 100% groundedness and citation accuracy observed in the evaluation.

### What didn't work
- **Local machine learning models on free tiers:** Attempting to run local ML models (like HuggingFace embeddings or CrossEncoders) on a 512MB RAM container was a complete failure. Cloud-native or serverless environments at this tier require offloading ML compute to external REST APIs.
- **Monolithic prototyping:** Starting the project as a single Streamlit monolith, while fast, created technical debt. Decoupling the app into a FastAPI backend and Streamlit frontend later required careful unpicking of the state management and routing logic.

### What could be approached better next time
- **API-first design:** Next time, I will start with a strict separation of concerns (FastAPI backend + UI frontend) from day one, rather than building a monolith and decoupling it later.
- **Resource profiling:** I will profile the memory footprint of core dependencies (like PyTorch) locally *before* attempting to deploy to a memory-constrained free-tier cloud host. This would immediately highlight the need for REST API embeddings without enduring deployment crashes.
- **Multi-turn testing:** The current evaluation script only tests single-turn questions. Future evaluations should include a multi-turn chat framework (using LangChain's `HistoryAwareRetriever`) to test context retention across a full conversation.
